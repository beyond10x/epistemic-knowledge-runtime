## Where practice diverges from the design

1. **Order.** The roadmap orders P2 → P3 → P4 (§ 5). We built slices of P3 and P4 before P2
   because the first consumer needed resolve and a viewer. P2 is now what blocks the consumer:
   without retained observations and evidence after the seed, every ingest reseeds a new store.
2. **The § 63 flow is skipped.** Design: observation → interpretation into a transient root →
   resolution → semantic decision → integration into canonical. Practice: an extraction outside
   the runtime → `ekr resolve` → assertions committed straight into canonical as `Proposed`.
   Nothing passes through an incubation root, and no interpretation session contract (A5) records
   what the extracting agent was given.
3. **Evidence granularity.** Invariant 4 requires sufficient provenance per assertion. Assertions
   cite a whole corpus file seeded as evidence, because evidence enters only through the seed; the
   per-message evidence lives outside the store.
4. **Throughput.** Design § 96 aims at one replay per command, but each command is its own
   process: on a 112 MB store one `ekr resolve` costs 2.94 s and `ekr head` 0.57 s (`epic:ingestion-throughput`). Object payloads
   are stored as JSON bytes inside event bodies (`task:object-payloads-belong-in-provider-blobs`),
   which is why the seed envelope is 39 MB for 11 MB of evidence.
5. **Held.** Deterministic validators, the canonical/transient type membrane, bitemporal
   assertions, replayability, bot-only publication and ESS-first data contracts all match the
   design.

## What success is

The consumer instance ingests every tracked source continuously and incrementally; each assertion
cites the one message it came from; agent-extracted knowledge passes through an incubation root
before canonical; agents read canonical state through MCP; the operator answers what the runtime
is unsure about. That is roadmap P2 + P3 + P4 exits, then P7 cut-over (release 0.1.0).

## Consumer priorities (2026-09-28, 0.0.12)

The first consumer instance ranked what it needs for its move from shadow to parity:

1. evidence after the seed (`story:add-evidence-operation`, blocked by `decision-blocker:evidence-entry-after-seed`);
2. write-verb cost (`task:write-verbs-cost-most-of-an-ingest`);
3. MCP read tools (`story:mcp-read-tools`);
4. `story:store-quality-report`, then `story:facts-migrate-across-schema-versions`, `story:types-merge-and-split` and `story:property-constraints-are-enforced`;
5. `story:session-starts-before-a-store`;
6. `story:store-provider-migration` and `story:store-equivalence-check`, not needed now.

It reports 0.0.12 working: apply over `ekr session` gives the same counts as one-shot calls on its fixture, with 16 processes instead of 44.

## Source order after chat (2026-09-28)

Relayed from the operator by the consumer instance: after chat, the sources it needs are GitLab
(merge requests, issues and the repositories hosted there), then Jira, then Confluence. For the P2
adapters this is the order GitLab, Jira, Confluence. The consumer also states its data policy:
improve existing data rather than delete it, and delete only when required; this matches
supersession and retraction keeping history, with physical deletion left to P6 maintenance.
