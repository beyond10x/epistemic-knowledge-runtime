approve

Owners: 0 findings. This is bounded implementation advice, not approval of an implemented residual-review path.

The smallest sound approach is one pure residual projection plus a replay-derived application progress record. Verify a human signature against its original historical material; separately derive permission to continue from that verified review and this application's subsequently verified commits. Do not compare an initial signed digest directly with a differently shaped post-schema digest, and do not infer progress from coincidentally matching current declarations or facts.

1. **Expose structured material before hashing.** Split `crates/ekr-kernel/src/schema_proposals.rs:289` into component construction and the existing digest assembly. Keep the original proposal document/digest and the existing no-progress /1 digest bytes unchanged. Add a crate-private projection input containing the verified application ID, ordered committed publication references and completed step keys. Use the frozen election/step identities to normalize proposed versus now-canonical allocations. A post-progress basis should explicitly hash application identity, proposal digest and ordered committed event/record/step/attempt references with the residual components under distinct domain tags; merely subtracting options without binding the prefix is insufficient.

2. **Progress comes from replay, not receipts or current-state matching.** Add a private replay-derived map keyed by application ID to `ReplayState` (`replay.rs:73`). Record a step as complete only after its guarded Commit occurrence has passed application authorization and ordinary commit replay, and the resulting revision is installed. Retain its exact step/item/mapping key, attempt ID, commit event/record reference and revision. Proposed, Validated, Stale, rejected, elected-only steps and completion receipts do not advance it. A missing completion receipt must not erase real progress. The current occurrence is never in the prefix used to authorize itself. Complete histories already bypass application replay caches; keep that policy initially rather than introduce another cache key.

3. **Project remaining work without rolling back the graph.** After verified schema completion, do not reapply the proposal's original additions through candidate(current_ontology, proposal): use the actual committed schema and frozen allocation correspondence, while still including dependency definitions needed by pending effects. Exclude only committed mapping keys belonging to this application, using full source-version/item/mapping-digest identity. Leave unrelated equal facts visible and pending. Do not remove arbitrary matching assertions or reset the graph to the proposal base. Keep the exact immutable correction list in the proposal/options; validate and project the still-pending all-corrections step. After its verified final commit, residual correction validation is empty and only recovery/reporting remains.

4. **Advance the authorized residual baseline only across verified own commits.** For a verified review, start with its exact historical projected components. Before each application occurrence, compare current residual evidence/options/effects with that review's expected residual at the already verified own prefix. After an authorized own Commit succeeds, recompute the residual on its actual post-commit graph and install it as the derived continuation baseline. This update is justified by the successfully verified predecessor material plus the exact approved step, not by accepting arbitrary current state. Unrelated commits never reset that baseline. Consequently an unrelated relevant change still requires review, whereas the application's own schema or mapped facts can legitimately change dependency/dispute material without forcing review merely for their occurrence.

   For a newer review, verify its signed basis at its own observed revision and own prefix. If already verified own commits lie between that basis and the current occurrence, advance its baseline through those exact commit boundaries, checking the pre-step residual before each advancement. Retain the needed pre/post graphs or their structured material during the same replay pass; do not jump directly to today's graph and call all differences permitted. A changed choice that would alter an already frozen pending transaction remains incompatible with that step and requires a new proposal/election.

5. **Use the same projector in all three callers.** Live Show and review retention currently use `schema_proposals.rs:143/168` and `schema_proposal_review.rs:282/309`; replay uses `application_auth.rs:315` and `reviews` at line 333. Route all through the same pure captured-input projector with a verified prefix scoped to the requested revision. `verify_captured_review` at schema_proposal_review.rs:60 must still compare the complete signed historical basis exactly. The direct three-digest comparison in application_auth.rs:798 is the continuation seam to replace with the expected-residual comparison above. Application-aware Show should expose the same verified prefix it hashes, not add independently re-read application presentation after computing a different basis.

6. **Break the replay cycles explicitly.** Do not implement the projector by calling verified_proposal_reviews, election, reconstruct, store.history or Commit::read. The current chain is already verify_occurrence -> election -> initial_review/reviews -> projected; calling authorization again from projected would recurse. The projection accepts only progress that replay has already admitted; it does not authenticate its own input by invoking that chain. Existing application_auth::at truncates revisions/answers/authority changes but leaves the transaction map at the later replay position. Therefore historical progress must be explicitly filtered by committed revision and already-verified occurrence boundary, or captured in a dedicated private per-revision progress snapshot; do not treat that transaction map as historical completeness. Extend replay.rs:1119's retained graph bases for the review and own-commit pre/post boundaries that the baseline derivation actually needs. Avoid graph_at fallback inside authorization, which can start another reconstruction.

7. **An unproposed mapping step has no invented historical resolution basis.** RetainedApplicationStep carries neither an elected canonical revision nor an elected review ID. For a step without a verified Propose occurrence, verify_history can check its immutable transport, selected item and mapping digests, pinned evidence/observation links, allowed operation shapes and identity invariants. It must not re-resolve aliases against today's graph and thereby poison previously readable metadata, or infer a canonical revision from elected_at. The first guarded Propose supplies the authenticated pre-occurrence read and effective review: derive expected mapping operations there, bind the already allocated IDs, compare the complete frozen transaction, then admit it. Preserve that semantic basis for historical verification; later Validate/Commit perform ordinary checks plus current residual authorization without retrospectively resolving the first proposal under a later graph. Reuse the retained pre-Propose graph/material in the same replay pass, not recursive reconstruction.

   This permits newly unblocked items to acquire their first step after a newer review, provided no step was previously elected for that item. If changed aliases/schema now require different operations for an already elected step, reapproval cannot change its frozen template: refuse that step and require a new proposal/election. Merely having an unproposed frozen step must neither count as committed progress nor make every subsequent read fail because current resolution differs. Show/residual review should distinguish its actual frozen effects and current incompatibility from the newly computed effects of an unelected item. Existing committed semantic resolution remains historical fact, not a dependency on today's aliases.

The expected residual is derived authority, not a newly signed human statement: retain the original verified proof/basis and the exact intervening permitted commit references. This separation implements design 105.17's distinction between an initial approval and later application-aware review without changing old signature bytes or treating an external coincidental effect as this application's progress. No new persistent semantic carrier or mutable progress registry is needed for the first implementation; existing elections, steps, attempts, guards and commits are sufficient inputs.

Minimum red-capable witnesses: initial approval continues through own schema and first mapped fact without rereview; an identical external schema/fact does not count as progress; unrelated nonmaterial advancement is harmless but changed pending resolution/dependency/dispute material stops; residual reapproval resumes unchanged allocations; old initial and newer residual signatures both verify on cold/full replay; a signed basis before a later own commit excludes that future prefix; removed/forged prefix references refuse; missing receipts recover; final corrections cannot authorize another canonical step. Include a material-change interleaving between two own commits so baseline advancement cannot silently bless external drift.

Limits: source/design advice over bd28c0644, not implementation or execution evidence. No source edits, Cargo, probes, AEP or external writes; only this sanitized report was written. Mapping builders remain coordinator work. Full F, conformance and delivery are not accepted here.
