**Findings, in priority order.** “Known” means the reviewed source or existing planning records already acknowledge the limitation. “Newly reproduced” means this review independently exercised the behavior; it does not imply nobody has ever noticed it elsewhere.

1. **High — the commit path is a revision demonstration, not a durable state transition. Known, independently reproduced.** A valid `CreateNode` returns revision 1, but the new node is absent from the folded graph. Dropping and reopening the SQLite store through `Commit::over` reports revision 0. Operations are hashed but not persisted/applied; validation authority is an in-memory `Rc<RefCell<BTreeSet<...>>>`. The source explicitly describes both limits. This is fairly treated as unfinished `story:commit-and-revision-lineage`, not as a surprise defect in a finished P1. However, callers already receive success from `commit`, and the implemented storage story's broad durability claim is not established for the real kernel path. Store reopen tests inject a stateless `Attesting` stub, which masks the kernel's lost authority. Close this with persisted transaction payloads, deterministic application and replay, and restart tests through the real kernel over both providers.

   Sources: [commit.rs:26](<workspace>/epistemic-knowledge-runtime/crates/ekr-kernel/src/commit.rs:26), [commit.rs:59](<workspace>/epistemic-knowledge-runtime/crates/ekr-kernel/src/commit.rs:59), [providers.rs:22](<workspace>/epistemic-knowledge-runtime/crates/ekr-store/tests/providers.rs:22), [test authority:59](<workspace>/epistemic-knowledge-runtime/crates/ekr-store/tests/lineage/mod.rs:59). Original design §§19, 34, 71–72.

2. **High — assertions bypass parts of declared type checking. Newly reproduced.** The full pipeline accepts an assertion using a relation restricted to Decision-node endpoints with a String object. It also accepts a `Type` object for a property declared `String`. The relation branch checks only that the edge type exists; the property/Type branch checks only that the property exists. Properties on edge and type subjects are skipped altogether. Since assertions are the design's fundamental knowledge primitive, validating direct edges and ordinary property values is insufficient. Enforce subject, predicate and object compatibility for every supported combination, and explicitly refuse unsupported combinations.

   Source: [types.rs:230](<workspace>/epistemic-knowledge-runtime/crates/ekr-kernel/src/validate/types.rs:230). Original design §§6.3, 12–13, 20–21.

3. **High — reference validation does not describe the transaction's resulting graph. Newly reproduced.** The pipeline accepts `DeleteEdge(e)` alongside an assertion whose subject is `e`. `Known::of` adds creations to the existing identity sets but never subtracts deleted edges. In contrast, the cardinality validator does subtract them. Thus two validators reason about different resulting states. This does not currently cause persisted corruption because operation application is unfinished, but it already produces a `ValidatedTransaction` that cannot satisfy the claimed no-dangling-reference invariant if applied as proposed. Construct or model one candidate post-state and validate it consistently.

   Sources: [reference.rs:176](<workspace>/epistemic-knowledge-runtime/crates/ekr-kernel/src/validate/reference.rs:176), [cardinality.rs:174](<workspace>/epistemic-knowledge-runtime/crates/ekr-kernel/src/validate/cardinality.rs:174). Original design §6.2.

4. **High — unsupported semantics are accepted rather than refused. Known deferrals, independently reproduced.** The pipeline accepts a new node type with a nonexistent parent, modification of a property no type declares, and invocation of an operation carrying a nonempty unsupported precondition. Deferring schema evolution and a constraint language is reasonable. Producing a validated transaction for those unsupported cases weakens the boundary. Reject unsupported operations and nonempty uninterpreted constraints until their semantics are implemented, or narrow the public contract explicitly.

   Sources: [types.rs:342](<workspace>/epistemic-knowledge-runtime/crates/ekr-kernel/src/validate/types.rs:342), [structural.rs:168](<workspace>/epistemic-knowledge-runtime/crates/ekr-kernel/src/validate/structural.rs:168), [ontology.rs:9](<workspace>/epistemic-knowledge-runtime/crates/ekr-kernel/src/validate/ontology.rs:9). Original design §§6.3, 6.9, 20; amendment 87.

5. **High — the seed/deserialization route bypasses graph validation. Known, independently reproduced.** A graph document containing an edge to a nonexistent node crosses `into_canonical` successfully. Filing, root identity, schema-version identity, and value admissibility are checked, but referential, type, lifecycle and acceptance/provenance validity are not. The existing independent review and ADR 0008 acknowledge this and place repair in the next debt wave. Until that repair lands, canonical Rust types are not evidence that loaded canonical state satisfies the invariants. Validate seeds at a deliberate trusted boundary before exposing them as canonical state.

   Sources: [snapshot.rs:48](<workspace>/epistemic-knowledge-runtime/crates/ekr-store/src/snapshot.rs:48), [snapshot.rs:222](<workspace>/epistemic-knowledge-runtime/crates/ekr-store/src/snapshot.rs:222), [ADR 0008](<workspace>/epistemic-knowledge-runtime/.engineering/planning/architecture-decision-record/0008-canonical-state-references-are-typed.md).

6. **Medium — transaction ordering needs a decision before application is implemented. Newly reproduced ambiguity.** The code says atomicity makes operations an unordered set. Atomicity does not itself imply order independence. Two conflicting updates to the same property both validate, with no rule in the validated representation resolving which value wins. The operation hash still follows vector order. Choose ordered execution or order-independent conflict rules explicitly, then make validation, hashing and application follow that contract.

   Source: [transaction.rs:168](<workspace>/epistemic-knowledge-runtime/crates/ekr-kernel/src/transaction.rs:168).

7. **Medium — repository correctness has no checked-in CI job.** The only workflow calls the shared security/privacy gate. I inspected the exact pinned reusable workflow from the local Gates repository; it deliberately does not execute candidate source. There is no checked-in job running `task check`. The local gate is valuable, but a green shared-source check is not a compilation/test/conformance result. Add a repository correctness job and require it before landing. Remote branch protection and live CI runs were not inspected: Connectors was healthy for local bounded calls but returned no admitted GitHub operations.

   Source: [shared-gates.yml:14](<workspace>/epistemic-knowledge-runtime/.github/workflows/shared-gates.yml:14), pinned Gates commit `a27a3bcfcabae584ec7b5252e58404b534fdb7f6`, `.github/workflows/common.yml`.

The own-kernel/eventlog decision, acyclic crate layering, and explicit canonical/transient representation are coherent choices. Float exclusion is recorded in ADR 0005. ADR 0007 explicitly narrows part of the writer guarantee to workspace dependency/source guards; that is a documented architectural tradeoff, not a fully type-enforced boundary against arbitrary external consumers.

The main unclosed design concession is the revision's ontology content. `ontology_root` is a fixed placeholder, while the caller supplies the ontology on reopen. Reproducing the knowledge hash therefore does not yet prove that the same schema governs that knowledge. The placeholder task expressly excludes this from P1, while the commit story still promises computation of all four sub-roots. Resolve that mismatch before claiming the phase's replay criterion; an absent agent registry can have a defined empty root, but an existing ontology should contribute its actual content.

**Planning quality: strong structure, uneven acceptance and follow-through.**

The roadmap has meaningful phase outcomes and examples, predecessor capabilities A1–A15 are assigned to phases, and later epics remain honestly draft. Stories name scopes and dependencies; decisions and reviews have durable records. Recent review findings changed actual code, and the coordinator recorded its own errors. These are useful controls.

Three weaknesses reduce the assurance those controls provide:

- Component acceptance is sometimes mistaken for runtime acceptance. The reopen tests establish provider behavior under a stub authority; they do not establish reopening the real kernel. A replay criterion must require an actual state change and a fresh-process read, not merely equality of unchanged hashes.
- Deferrals are visible but not consistently scheduled. The unauthenticated-proposer task literally calls its obligation unowned and names possible future owners in prose; it has no dependency on the submission story. The placeholder-root task likewise has no blocking relation to the commit story. `aep plan artifact blocked` still lists an implemented store story behind a draft membrane task and also reports completed blocking tasks. Validation of the store does not mean its scheduling state is coherent.
- Upcoming story acceptance has drifted from current code: commit/revision still asks for `active()`, which the graph deliberately removed, and promises all sub-roots despite the placeholder task's different P1 boundary. Reconcile contracts before dispatch rather than transferring contradictions to implementors.

**Implementation quality: careful local Rust work, weaker integration evidence.** Public types and errors are explicit, unsafe code is forbidden, the kernel is deterministic and model-free, and the suite contains useful positive, negative, property and compile-fail tests. Approximately 10,082 lines under crate `src/` and 19,957 under crate `tests/` show substantial effort; these counts include comments and do not measure correctness or coverage.

Several guards inspect source strings, names or comments. They help detect drift, but cannot demonstrate that a behavior is enforced. The known compile-time `CARGO_MANIFEST_DIR` issue can also make such guards read another checkout when artifacts are reused; the fresh target directory avoided that problem in this review. The repository's own public-surface guard explicitly says it is not coverage. Keep those checks, but make the main assurance behavioral and cross-crate.

The documentation is unusually candid about limitations, but large module comments often mix the current contract with a history of prior reviews and repairs. Keep current invariants concise in source and move most incident history into linked ADRs/reviews. Also update the README: its claim that the six crates are empty is obsolete.

**Recommended next order.** First repair assertion/post-state validation and close the seed crossing. Refuse unsupported schema/constraint cases. Then deliver one real seed → validate → apply → persist → restart → query path through both backends, with a changing graph hash and an ontology-bound revision. Exercise stale commits, interrupted writes/retries, retraction, and reconstruction at an earlier revision. Reconcile the commit story and attach deferred obligations to concrete owners. Add repository correctness CI, then finish CLI and ESS conformance before moving to P2.
