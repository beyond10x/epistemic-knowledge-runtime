## Design decisions taken for the operator (defaults from the scoper, approved with the wave)

1. Schema changes go in schema-only transactions: a transaction mixing a schema operation with any
   other operation is refused with a named issue. Mixed transactions are a later milestone.
2. Validation profile v2 is `ekr.p2-deterministic/1` + `ekr.p2-apply/1`. A store keeps the profile
   its authority anchor names at seed; v1 stores keep replaying under v1 and refuse the three schema
   operations with a named issue. Moving an existing store to v2 needs an authority change that no
   mechanism provides yet; that is a later milestone, not this wave.
3. A schema-changing transaction carries the new `SchemaVersionId` (from `ekr mint schema-version`) in
   one optional transaction field, required exactly when a schema operation is present. A transaction
   without it encodes byte-identically to today, so no legacy vector moves.
4. `GraphRoot.schema_version_id` stays the seed's (root identity); the ontology root carries each new
   version with number + 1 and parent = the prior version.
5. `ModifyProperty` gains an owner type. Its payload and canonical encoding change; the three kinds
   had no committed instances, since P1 refused them.
6. Removing a type is out of scope: no operation removes one.
