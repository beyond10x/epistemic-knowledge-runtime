Epistemic Knowledge Runtime

Knowledge you
can explain.

Keep facts typed, backed by evidence and open to revision. EKR gives people and agents a shared knowledge store where every accepted change has been validated, and every assertion can be traced to its source.

Built in Rust · File or SQLite storage · Apache-2.0

01 / The validation boundary

Agents propose.
The kernel validates.

Start with a schema: node types, edge types, typed properties and lifecycles. Every ordinary change then follows the same path to canonical knowledge.

  1. 01 / Propose

    Describe the change

    Submit a transaction with the facts, relationships and evidence you want to record.

  2. 02 / Validate

    Check the contract

    Deterministic validators check identities, references, types, provenance and revision lineage.

  3. 03 / Commit

    Keep the history

    A validated transaction becomes a new immutable revision. Later corrections add history rather than erase it.

Validation checks the declared rules. It does not establish that a claim is true merely because an agent supplied it.

02 / A first store

From an example
to an explained fact.

Build the CLI, then use its matching example documents to seed a store and commit an assertion. Run the example in a fresh directory.

Build and install

With Git and Rust installed, the repository’s pinned toolchain builds the ekr binary.

git clone https://github.com/beyond10x/epistemic-knowledge-runtime.git
cd epistemic-knowledge-runtime
cargo build --locked --release -p ekr
install -Dm755 target/release/ekr "$HOME/.local/bin/ekr"
export PATH="$HOME/.local/bin:$PATH"

For configuration and storage options, see the installation guide.

Record, validate, explain

ekr example ekr.cli-host/1 > host.json
ekr example ekr-seed/2 > seed.yaml
ekr example ekr.transaction-document/2 > change.yaml
export EKR_HOST=host.json EKR_STORE=./store EKR_BACKEND=file

ekr seed seed.yaml
ekr propose change.yaml
ekr validate 00000000-0000-4000-8000-000000000601
ekr commit 00000000-0000-4000-8000-000000000601
ekr explain 00000000-0000-4000-8000-000000000501

The IDs belong to these example documents. For your own data, use ekr mint and read existing IDs from the store.

What to expect

validate answers Validated; commit creates revision 1. explain returns the assertion, its evidence and its history as JSON. Use ekr guide for the workflow from the binary itself.

03 / What you can use

One store.
Several ways to understand it.

The runtime holds structured knowledge and the context needed to revisit it.

Model

A vocabulary you own

Define typed nodes, relationships, properties and lifecycles. Supported validation profiles let the schema grow through committed transactions.

Trace

Evidence and explanations

Retain evidence, explain an assertion and attach further evidence to an active accepted claim. Retract or supersede it when knowledge changes.

Revisit

History and valid time

Read snapshots and schemas at a revision, ask what was believed at a valid time, and replay the history behind the current state.

Explore

Readable graph views

Search, inspect neighbourhoods and follow timelines. ekr view serves a local read-only graph viewer; OCEL export supports event-log analysis.

Integrate

CLI, SDK and MCP

Use JSON commands, a persistent ekr session, or the typed Rust SDK. The MCP server gives agents read-only tools to explore and explain knowledge.

Assess

Inspect knowledge quality

Check evidence coverage, inspect rejected transactions and draw reproducible fact samples. Your consumer supplies the judge and judgement policy.

04 / Current scope

A working core.
An evolving runtime.

The released core includes typed knowledge, validated transactions, evidence, temporal reads, the SDK and read-only MCP. File and SQLite providers share the validation boundary.

Browse releases ↗

What is still ahead

Continuous source ingestion, the incubation forest, schema discovery from evidence and maintenance belong to later phases. The MCP surface does not provide writes.

Some declared constraints and operation semantics are not implemented; affected writes receive named refusals. Consult the current status before relying on a capability.
