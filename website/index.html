01 / Beyond a knowledge graph

The graph is the structure.
The knowledge has a lifecycle.

EKR combines typed graph storage with rules for admitting claims, retaining their support and revising them without losing the past. The distinction is that these responsibilities belong to the runtime’s write path and history.

Acceptance

Who accepted this, and why?

Trace an assertion through its proposal, deterministic validation and commit to its evidence. Proposer and validator must have distinct identities; validation does not rely on a model.

Support

What is the claim based on?

Assertions carry evidence whose exact bytes are retained. Add new support to an accepted, active claim without replacing the original assertion. Ordinary node properties remain attributes, not evidence-bearing claims.

Revision

What changed in our knowledge?

Retract or supersede a claim while keeping its explanation. Query what the store knew at a revision separately from when a claim held in the world.

A correction should teach you something.

Imagine an incident first recorded as severity 2, then corrected to severity 1 from 10:30. EKR can preserve the earlier belief, the correction’s evidence and the new claim’s valid time. Reading an earlier revision still shows what was known then.

Other graph systems can support provenance and time too. EKR’s focus is bringing them together with governed acceptance and revision for people and agents.

02 / The validation boundary

Agents propose.
The kernel validates.

Start with a schema: node types, edge types, typed properties and lifecycles. Every ordinary change then follows the same path to canonical knowledge.

  1. 01 / Propose

    Describe the change

    Submit a transaction with the facts, relationships and evidence you want to record.

  2. 02 / Validate

    Check the contract

    Deterministic validators check identities, references, types, provenance and revision lineage.

  3. 03 / Commit

    Keep the history

    A validated transaction becomes a new immutable revision. Later corrections add history rather than erase it.

If the store advances after validation, commit returns Stale: the decision must be revisited. Validation checks declared rules; acceptance is not proof that a claim is true.

03 / A first store

From an example
to an explained fact.

Build the CLI, then use its matching example documents to seed a store and commit an assertion. Run the example in a fresh directory.

Build and install

With Git and Rust installed, the repository’s pinned toolchain builds the ekr binary.

git clone https://github.com/beyond10x/epistemic-knowledge-runtime.git
cd epistemic-knowledge-runtime
cargo build --locked --release -p ekr
install -Dm755 target/release/ekr "$HOME/.local/bin/ekr"
export PATH="$HOME/.local/bin:$PATH"

For configuration and storage options, see the installation guide.

Record, validate, explain

ekr example ekr.cli-host/1 > host.json
ekr example ekr-seed/2 > seed.yaml
ekr example ekr.transaction-document/2 > change.yaml
export EKR_HOST=host.json EKR_STORE=./store EKR_BACKEND=file

ekr seed seed.yaml
ekr propose change.yaml
ekr validate 00000000-0000-4000-8000-000000000601
ekr commit 00000000-0000-4000-8000-000000000601
ekr explain 00000000-0000-4000-8000-000000000501

The IDs belong to these example documents. For your own data, use ekr mint and read existing IDs from the store.

What to expect

validate answers Validated; commit creates revision 1. explain returns the assertion, its evidence and its history as JSON. Use ekr guide for the workflow from the binary itself.

More than storage.
Already in the runtime.

Shipped / Support that grows

New evidence, same assertion

Attach evidence to an accepted, active assertion. The attachment has its own revision; earlier snapshots stay unchanged, and superseding the claim leaves its support with the original.

Shipped / Extraction application

Repeat an import, not its facts

apply-extraction applies a consumer’s structured extraction through validated transactions. Reapplying the same document adds nothing; ambiguous references are reported rather than guessed.

Extraction and progress reports ↗
Shipped / Typed identity

Names are not identities

Resolve typed references and aliases to stable IDs, a proposed new entity or an explicit ambiguity. A shared name is not permission to silently merge two entities.

Shipped / Two views of time

Then, and what we knew then

Use --at to read a stored revision and --valid-at to filter by a claim’s valid time. Immutable history and replay preserve how the store arrived at its current state.

Shipped / Measurable quality

Sample, judge, report uncertainty

Draw reproducible fact samples, supply your own judge and report the pass rate with a Wilson confidence interval. Inspect evidence coverage separately: having a source is not the same as being correct.

Shipped / Explicit schema evolution

The vocabulary has history too

Grow the schema through explicit, versioned transactions under supported validation profiles. Inspect the schema at a revision alongside the knowledge it described.

Use it from your own tools.

05 / Planned, not yet shipped

From a governed core
to a learning loop.

The direction is a runtime that notices gaps, preserves unresolved observations and proposes improvements. These loops are roadmap work, not promises of today’s CLI.

Planned / Incubation and disagreement

Keep what does not fit yet

An incubation forest would hold observations in local schemas until they can be integrated. Contradictory claims become explicit disputes; entity merge and split preserve lineage.

Planned / Evidence-led schema discovery

Let observations challenge the model

Discover schema changes from parked knowledge, with migration plans and approvals matched to risk. Explicit schema evolution already works; discovery and these approval loops are ahead.

Planned / Observation and attention

Choose what to learn next

A knowledge frontier would prioritize gaps, source refreshes and questions for people. Scheduled observation uses explicit budgets and stop conditions; source connectors belong in consumers.

Planned / Maintenance

Retire knowledge deliberately

Retention, consolidation, decay and erasure would account for dependent claims. The aim is maintained knowledge whose changes remain explainable, including what loses its support.

Read the phased roadmap ↗

Today, consumers supply extraction, source integration and model judges. Some declared operations remain unsupported and return named refusals; consult the current status for the exact boundary.
